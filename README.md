# stock-research-agent

**멀티홉 에이전틱 RAG 종목 리서치 어시스턴트.** "SK하이닉스 9월 주가 상승이 실적 때문이야?", "반도체 소재주 중 영업이익률 1위는?" 같은 복합 질문을 LLM 플래너가 쪼개고, DART 재무·뉴스·주가·업종 비교 네 가지 도구(+ 필요할 때만 기사 본문 읽기) 중 필요한 것을 골라 여러 번 호출한 뒤, 근거를 인용해 답합니다.

이 프로젝트의 핵심 질문은 **"도구를 상황에 맞게 골라 쓰는 에이전트가 고정 파이프라인보다 실제로 나은가?"** 이고, 이를 자동 채점 파이프라인으로 측정합니다.

전체 설계/계획: [Notion 계획서](https://app.notion.com/p/3e43a009bcdf8178861eecf2eb6ad11e)

## 구조

```
질문 ─▶ (대화 메모리: 이어지는 질문을 독립된 질문으로 재작성) ─▶ 플래너 (src/agent/planner.py, ReAct 루프, 계획은 gpt-5.4-nano, 최대 7스텝)
          │  질문의 전제("올랐다/줄었다")부터 데이터로 확인 → 필요한 도구 선택 → 결과 보고 재시도
          ├─▶ get_financial_data  DART 재무제표 (전년 동기·전기말 비교값, 연도 지정, 조회 가능 보고서 목록)
          ├─▶ search_news         NAVER 실시간 검색 + bge-m3 재정렬 (기간 필터, 페이지 넘김, 중복 기사 제거)
          ├─▶ get_stock_price     KRX 주가·기간 수익률·PER/PBR/시가총액 (pykrx)
          ├─▶ compare_peers       같은 업종 회사들의 재무 지표 순위 (핵심 종목군 50개사 기준)
          └─▶ read_articles       검색 요약만으로 부족할 때만, 고른 기사 1~3개의 본문 앞부분
          ※ 재무 질문인데 재무 도구를 안 불렀으면 코드가 한 번 되돌려 조회하게 함
        ─▶ 초안 답변 ─▶ 검증 단계 (gpt-5.4-mini가 조회 자료와 대조: 틀린 수치 수정, 근거 없는 주장 삭제, 모순 정리)
        ─▶ 근거를 인용한 최종 답변
```

### 지원 종목

- **핵심 종목군 50개사 (미리 수집)**: 반도체 밸류체인 22개사(메모리·파운드리·전공정 장비·후공정 장비·소재·부품·테스트·패키징·기판으로 세부 업종 분류) + 코스피 시가총액 상위 30개사(2026-09-23 스냅샷, 우선주 제외). 업종 비교(`compare_peers`)는 이 종목군 안에서 합니다.
- **그 밖의 회사 (요청 시 수집)**: DART에 공시하는 회사라면 처음 물을 때 DART에서 받아 로컬 DB에 저장하고, 이후엔 DB에서 바로 읽습니다 (처음 1회 약 3초). "네이버→NAVER", "현대차→현대자동차" 같은 흔한 별칭을 인식하고, 이름을 못 찾으면 비슷한 상장사 이름을 알려줘 에이전트가 다시 조회합니다.

| 경로 | 내용 |
|---|---|

| `data/universe_snapshot.json` | 핵심 종목군 스냅샷 (시가총액 순위를 날짜로 고정해 평가를 재현 가능하게) |
| `src/agent/tools.py` | 도구 5개 (OpenAI function calling 스키마 + 실행 함수) |

| `src/eval/` | 골든셋, 채점기, LLM 심판, 도구 호출 경로 분석, 실험 러너 (Phase 5) |

## 평가 설계

### 비교군 (도구 구현은 모두 동일, 다른 건 "도구를 어떻게 조합하느냐"뿐)

| 방식 | 동작 |
|---|---|
| DART-only 고정 파이프라인 | 재무 도구만 1회 호출(최신 보고서) 후 답변 |
| News-only 고정 파이프라인 | 질문을 검색어로 1회 변환 → 뉴스 1회 검색 후 답변 |
| 항상 모든 도구 고정 파이프라인 | 질문과 무관하게 모든 도구를 고정 인자로 1회씩 호출(최신 보고서, 최근 30일 주가, 영업이익률 업종 비교, 뉴스 상위 3개 본문) 후 답변 ("그냥 다 부르면 되지 않나?"를 검증하는 가장 강한 비교군) |
| **플래너 에이전트** | 필요한 도구만 골라 여러 번 호출, 결과를 보고 재시도, 답변을 조회 자료로 한 번 더 검증 |

공정한 비교를 위해 네 가지를 맞췄습니다: 도구 함수 동일, 프롬프트 규칙(`prompts.py`) 공유, 출력 길이 제한 동일, **최종 답변 모델 동일(gpt-5.4-mini)**. 고정 파이프라인에는 질문 속 회사명을 미리 알려줘서 오히려 유리한 조건입니다. 반대로 "재무 도구 강제"와 "검증 단계"는 에이전트에만 있는 단계이므로, 결과 차이 중 일부는 이 단계 덕분입니다.

### 골든셋 (`src/eval/gold_set.py`)

- **튜닝 셋 11문항**: 재무 수치, 실적·주가 원인, 주가/PER, 재무 비율·기업 비교, 잘못된 전제. 개발 중 이 질문들을 보고 프롬프트·채점기를 고쳤기 때문에 **점수가 과대평가될 수 있습니다.**
- **held-out v1 6문항**: 부채비율, 매출 성장률, 다른 기간 수익률, PBR, 재무 데이터로 잘못된 전제 교정, 주가+재무+뉴스 멀티홉. 개발 중 h5를 보고 에이전트·채점을 고쳐 **일부 오염**됐습니다.
- **held-out v2 6문항**: 2025년 연간·3분기 보고서, 순이익률, "더 낮은 쪽" 기업 비교, 반대 방향 주가 전제, PER 밸류에이션 판단. 이후 v2에서 도구 결함(연도 지정)을 발견해 고쳤습니다.
- **held-out v3 6문항 (주 지표)**: 지원 종목 확장·업종 비교·답변 모델 분리 이후 결과를 보기 전에 확정. DB에 없던 회사(크래프톤), 별칭(네이버), 업종 1위, 경쟁사 대비 위치, 새 회사의 과거 연도, 업종 비교+뉴스 멀티홉.
- 정답값은 하드코딩하지 않고 **채점 시점에 DART DB·KRX에서 직접 계산**합니다. 업종 1위 문항의 정답은 에이전트 도구와 같은 계산으로 만듭니다.

### 지표

| 지표 | 무엇을 재나 | 방법 |
|---|---|---|
| 수치 정확도 | 답변 속 숫자가 정답과 맞는지 | 규칙 기반. 조/억/만·%·배 표기를 파싱해 원본값과 대조 |
| 인용 P/R/F1 | 필요한 출처(도구)를 썼는지 | 질문별 정답 출처 라벨 vs 실제 호출한 도구 |
| LLM 심판 | 결론의 정확성·일관성, 원인 설명, 전제 교정, 근거 충실도(환각) | gpt-5.4-mini가 채점 기준 + 참고 정답 + **답변자가 조회한 자료**를 보고 pass/fail. 수치 일치는 코드 결과를 넘겨줌 |
| 쌍대 비교 | 에이전트 vs 3도구 항상 호출, 어느 답이 나은지 | A/B 순서를 바꿔 두 번 판정, 엇갈리면 무승부 (위치 편향 제거) |
| 도구 호출 경로 | 호출 수, 중복 호출, 결과가 빈 호출 | 저장된 실행 기록으로 계산 (API 호출 없음) |

**LLM 심판 자체도 검증했습니다.** 사람이 pass/fail을 매긴 7개 답변으로 심판과의 일치율을 쟀습니다:

| 심판 설정 | 사람 판단과 일치 |
|---|---|
| gpt-5.4-nano, 초기 | 4/7 |
| + 수치 확인은 코드에 맡기고 채점 기준 명확화 | 17/21 (7건 × 3회) |
| + 조회 자료 제공 (nano는 긴 입력에서 규칙을 어김) | 13/21 |
| **gpt-5.4-mini로 교체** | **21/21, 반복 판정 흔들림 없음** |

### 해석

- **답변 모델을 키우자 "그냥 다 부르는" 방식이 많이 따라왔습니다.** 튜닝 셋에서는 동점(9/11)이 됐어요. 최신 보고서·최근 30일처럼 **기본 인자로 필요한 정보가 다 들어오는 질문**은, 답변을 잘 쓰기만 하면 도구 선택 없이도 풀리기 때문입니다. 즉 예전에 보였던 격차 중 상당 부분은 "구조"가 아니라 "답변 품질" 차이였습니다.
- **에이전트의 구조적 우위는 기본 인자로 못 가져오는 정보가 필요한 질문에 남습니다.** 특정 연도·기간(2025년 연간, 1~9월 누적, 8월 수익률), 두 회사 비교, 경쟁사 대비 위치, 잘못된 전제 교정 — 이 유형(v2_1, v2_2, v2_4, v2_5, v3_4, v3_5)은 "항상 모든 도구"가 **전부 실패**하고 에이전트는 **전부 통과**했습니다. 이게 이 프로젝트가 증명하는 핵심입니다.
- **에이전트가 밀린 문항**: v3_3(업종 1위, 심판 탈락)은 도구 버그 — 에이전트가 "반도체 소재"로 불렀는데 업종 이름이 정확히 "소재"여야만 인식했습니다. 수정했지만 v3 점수는 수정 전 그대로 둡니다. v3_2(별칭)는 금액을 맞게 조회해 놓고 "약 6,629.8억 원"으로 단위를 잘못 환산했습니다(실제 6조 6,298억). 심판은 통과시켰지만 쌍대 비교에서 져서 드러난 오류로, 프롬프트를 고치지 않고 약점으로 기록만 해 둡니다 (held-out 결과를 보고 튜닝하지 않기 위해).
- **1회 실행이라는 한계는 그대로입니다.** 같은 질문에서도 실행마다 에이전트 행동이 달라지는 것을 확인했습니다.

## 지연 시간·비용 개선

같은 자료를 매번 새로 가져오던 구조를 바꿨습니다.

| 개선 | 내용 |
|---|---|
| 뉴스 검색 결과 캐시 | 이미 끝난 기간의 결과는 계속 재사용, 최근 기간은 1시간 |
| 뉴스 아카이브 (메모리) | 가져온 기사를 모두 로컬에 쌓고, 기간 지정 검색 때 NAVER 결과와 합침. NAVER가 최근 1,000건까지만 보여주는 한계가 시간이 갈수록 완화됨 |
| 임베딩 캐시 | 같은 기사를 다시 벡터로 바꾸지 않음 |
| 주가·회사 정보 캐시 | 지난 날짜 주가는 영구, 오늘 포함은 10분, 회사 개요는 30일 |
| 기업 목록 메모리 적재 | 회사명→코드 변환마다 30MB 파일을 다시 읽던 것을 1회로 (재무 조회 0.17초 → 0.076초) |
| 도구 병렬 실행 | 한 단계에서 요청한 도구들을 동시에 실행하고, 독립적인 조회는 한 번에 요청하도록 유도 (단계 수가 줄면 매번 다시 보내는 대화 이력도 줄어 토큰이 절약됨) |
| 사용량 기록 | 모든 LLM 호출의 입력·출력·캐시 적중 토큰을 기록해 방식별로 비교 (`run_phase5` 요약 표) |

### 대화 메모리 · 기사 본문 · 배치 수집

| 기능 | 방식 | 왜 이렇게 |
|---|---|---|
| 대화 메모리 (`src/agent/memory.py`) | 이어지는 질문을 이전 대화(최근 3턴)를 보고 혼자서도 뜻이 통하는 질문으로 다시 쓴 뒤 에이전트에 넘김. 대화는 SQLite에 저장돼 재시작 후에도 이어짐 | 이전 대화·도구 결과를 통째로 계속 붙이면 턴마다 입력 토큰이 수천씩 불어남. 질문 한 줄만 다시 쓰면 입력이 일정하고, 이전 턴의 조회 결과는 도구 캐시에 있어 다시 조회해도 API를 안 부름. 첫 질문은 LLM 호출 없음 |
| 기사 본문 읽기 (`read_articles` 도구) | 검색 결과에 기사 id를 붙이고, 요약만으로 원인이 불분명할 때만 에이전트가 1~3개를 골라 본문 앞부분(1,500자)을 읽음. 동시 수집, 본문은 영구 캐시 | 매번 본문을 다 붙이면 느리고 토큰이 5배 이상. 사이트별 크롤러 대신 NAVER 뉴스 페이지(언론사 무관 구조 동일) 파서 1개 + 공통 규칙(글이 가장 많이 모인 블록) 1개로 처리 — 비NAVER 기사 40개 중 37개 성공, 실패하면 "못 가져옴"을 그대로 알림 |
| 배치 뉴스 수집 (`src/data/collect_news.py`) | 50개 종목 × 2개 검색어를 최신순으로 넘기며 아카이브에 쌓음. 한 페이지가 전부 이미 가진 기사면 멈춤 | NAVER는 최근 1,000건까지만 보여줘서, 질문이 올 때만 검색하면 과거 기간 기사에 빈틈이 생김. 매일 돌리면 검색어당 1~2번 호출로 끝남. 실측: 첫 실행 NAVER 994번·580초로 아카이브 300건 → 52,713건, 바로 이어 돌린 두 번째 실행은 검색어 100개에 약 1번씩 |
| 임베딩 미리 계산 (`--embed-days`) | 최근 N일 기사를 수집 시점에 임베딩 | 뉴스 검색 지연의 대부분(수집 기사 80건 재정렬에 CPU 10초 이상)이 임베딩 계산. 미리 해두면 검색 때는 질문 문장만 임베딩. 실측(최근 3일 3,951건, CPU 778초): 새로 임베딩할 기사가 4건이면 검색 1.3초, 15건이면 3.6초, 대상 기간 밖 기사가 많아 81건이면 17.2초 — 지연은 새로 임베딩하는 기사 수에 비례 |
| 대화 모드 (`python -m src.agent.chat`) | 프로세스를 띄워둔 채 대화, 시작하자마자 임베딩 모델(2GB)을 백그라운드 스레드에서 미리 로딩 | 모델 로딩 11초를 사용자가 첫 질문을 입력하는 시간 뒤로 숨김 |

**실제 대화 예시** (2026-09-26, 두 번째 질문은 메모리가 없으면 뜻이 통하지 않음)

```
질문> 삼성전자 2026년 상반기 영업이익이 왜 늘었어?
  · get_financial_data(삼성전자, h1, 2026) 0.18초
  · search_news × 3 (실적 발표 / 메모리 업황 / 환율, 2026-01-01~08-31) 동시 실행

삼성전자 2026년 상반기 영업이익은 늘었습니다. 상반기 누적 146조 7,252억 원 (전년 동기 11조 3,613억 원) ...

질문> 그럼 SK하이닉스는?
  (이해한 질문: SK하이닉스 2026년 상반기 영업이익은 왜 늘었어?)
  · get_financial_data(SK하이닉스, h1, 2026) 0.01초
  ...
SK하이닉스 2026년 상반기 영업이익은 늘었습니다. 상반기 누적 98조 1,528억 9,100만원 (전년 동기 16조 6,533억 5,500만원) ...
```

**검토했지만 하지 않은 것**
- **사이트별 크롤러**: 언론사마다 파서를 두면 사이트 구조가 바뀔 때마다 깨지고 관리 비용이 큽니다. NAVER 뉴스 페이지 + 공통 규칙으로 대부분 해결돼 필요성이 낮았습니다.
- **임베딩 모델 int8 양자화**: CPU에서 1.7배 빨랐지만 검색 결과 상위 5개가 평균 4개만 같았습니다. 속도를 위해 검색 결과가 바뀌면 이전 평가와 비교할 수 없게 되어 적용하지 않았습니다.
- **asyncio 전환**: 한 단계의 도구 호출은 이미 스레드로 동시에 실행합니다. 동시 호출이 많아야 4개라, 비동기로 바꿔도 이득이 거의 없습니다.

## 개발 중 발견한 문제와 해결

평가를 만들면서 발견한 문제들입니다. 대부분 "비교가 공정하지 않았다" 또는 "채점이 틀렸다" 유형이었습니다.

- **API 키 로드 누락**: 클라이언트 코드 어디에도 `load_dotenv()`가 없어, 셸에 키를 export하지 않으면 DART가 HTML 에러 페이지를 반환 → 추가
- **News-only 비교군이 질문 문장을 그대로 검색어로 사용**: 에이전트만 검색어를 만들고 있어 불공정 → 비교군에도 검색어 생성 단계 1회 추가
- **골든셋 문구의 모호함**: "반기 매출액"이 분기 단독(171조)과 상반기 누적(305조) 둘 다로 읽혀 채점이 운에 좌우됨 → "1~6월 누적"으로 명시
- **비교군만 답변을 300토큰으로 자름**: 수치를 말하기 전에 답변이 잘려 불공정 → 제한 제거
- **심판이 "305조 3,729억"을 원 단위와 대조하지 못함**: 친절한 한국어 단위를 쓰는 답변만 불리 → 수치 확인은 코드가, 심판은 논리만
- **검색 기간 규칙 결함**: "보고서 기간 안에서만 검색"하게 했는데, 실적 원인 기사는 대부분 기간이 끝난 뒤 실적 발표 때 나옴 → 기간 종료 후 2개월까지 검색
- **에이전트 자기모순**: 계산 전에 결론부터 써서 "삼성전자가 더 높다… 따라서 SK하이닉스가 더 높다"가 두 번 재현 → "계산 먼저, 결론은 마지막에 한 번" 규칙
- **재무 도구 없이 수치를 지어냄**: "영업이익이 왜 줄었어?"(실제로는 증가)에 대해 재무 도구를 부르지 않고 전년 수치를 115.8조로 지어내(실제 16.7조) 틀린 전제를 받아들인 실행이 있었음 → 재무 용어가 있는 질문에서 재무 도구를 안 불렀으면 코드가 한 번 되돌림. **held-out(h5)에서 발견한 문제라, 이 수정 이후 h5는 깨끗한 held-out이 아닙니다.**
- **근거 없는 원인 끼워 넣기, 결론 모순**: 기사를 찾아와도 자료에 없는 원인("성과급")을 넣거나 "전제가 맞습니다… 증가했습니다"처럼 앞뒤가 다른 답이 나옴 → 초안을 조회 자료와 대조하는 검증 단계 추가
- **채점 기준이 환각을 부추김**: "원인을 최소 2가지 제시", "세 카테고리 모두 근거 있는 원인" 같은 기준은, 근거가 원인 하나만 뒷받침할 때 나머지를 지어내야 통과하는 구조였음 → 개수 대신 "근거 있는 원인 제시, 못 찾은 부분은 솔직히 밝히면 통과, 지어내면 fail"로 수정 (튜닝 셋 q5·q6만. held-out은 그대로)
- **증가율 문항의 수치 채점 설계 오류**: 증가율(%)만 정답으로 봐서, 금액 두 개("전년 16.7조 → 당기 98.2조")로 답하면 틀린 것으로 처리됨 → 금액 두 개를 정확히 제시해도 정답으로 인정. held-out(h5) 채점 방식을 결과를 본 뒤 고친 것이라 명시해 둡니다 (모든 방식에 똑같이 적용).
- **재무 도구에 연도 지정이 없음**: "2025년 1~9월 누적 영업이익"에서 에이전트가 최신 보고서만 보고 포기함. 도구가 연도를 받지 않고 조회 가능한 보고서 목록도 주지 않아 재시도할 단서가 없었음 → `year` 파라미터와 보고서 목록 추가. held-out v2에서 발견했으므로 v2 점수는 수정 전 결과로 둠
- **채점기 정규식 버그**: 조/억/만 금액 패턴이 숫자 없이 쉼표만 있어도 매칭돼, 답변에 "비용, 억제" 같은 표현이 나오자 `", 억"`을 금액으로 읽으려다 채점이 멈춤 → 숫자로 시작해야 매칭되게 고치고 단위 테스트 추가
- **뉴스 검색이 첫 페이지만 봄**: 첫 100건은 인기 종목이면 최근 두 달치뿐이라 몇 달 전 기사가 "존재하는데도" 못 가져옴 → 기간 지정 시 최대 10페이지(1,000건)까지 넘겨 수집하고, 임베딩 전에 키워드 사전 필터로 80건으로 줄임 (CPU에서 500건 임베딩이 66초라서). 튜닝 셋에서 0건이던 검색어가 기간 내 기사 184~514건으로 늘었습니다. 대가로 기간 지정 검색 한 번에 18~35초가 걸립니다.

- **Windows 보안 정책이 임베딩 라이브러리를 차단**: sentence-transformers가 불러오는 pyarrow DLL을 Windows 애플리케이션 제어가 막아 뉴스 검색이 통째로 실패 → transformers로 직접 임베딩(CLS 토큰 + 정규화)하도록 바꿈. 불필요한 의존성이 빠지며 약 3배 빨라짐
- **DART가 빈 금액을 "-"로 보냄**: 보험사 등을 수집하다 `int("-")`에서 멈춤 → 빈 값으로 처리하고, 종목 하나가 실패해도 전체 수집은 계속되게 함
- **도구 예외가 에이전트 전체를 멈춤**: 없는 회사명 등으로 도구가 예외를 던지면 실행이 중단됨 → 예외를 도구 결과("찾지 못함 + 비슷한 이름 후보")로 돌려줘 에이전트가 스스로 고쳐 부르게 함
- **은행과 지주사가 같은 업종으로 묶임**: SK·SK스퀘어와 은행들이 같은 업종 코드(64992)라 영업이익률 비교가 무의미해짐 → 매출액 계정 유무로 한 번 더 나눔
- **업종 이름 인식 실패 (held-out v3_3)**: 에이전트가 "반도체 소재"로 부르면 업종 이름이 정확히 "소재"가 아니라서 못 찾음. 고친 뒤에는 "전공정 장비"가 "후공정 장비"까지 잡는 2차 버그 → 업종 이름이 정확히 일치하면 그것만, 아니면 단어 단위로 매칭. v3 점수는 수정 전 그대로 보고
- **기업 목록 파일을 호출마다 다시 읽음**: 캐시를 붙인 뒤 측정해 보니 재무 조회가 여전히 호출당 0.17초 — 30MB 기업 목록 JSON을 매번 파싱하고 있었음 → 프로세스당 한 번만 읽도록 (0.076초)
- **병렬 실행 뒤 호출 수 카운터 경합**: NAVER 일일 호출 수를 JSON 파일로 세고 있었는데, 뉴스 검색을 동시에 돌리고 배치 수집기까지 같이 돌자 반쯤 쓰인 파일을 읽어 검색이 `JSONDecodeError`로 실패함 (호출 수도 빠짐) → SQLite 트랜잭션으로 원자적으로 셈. 스레드 16개로 800번 올려 정확히 800 증가 확인
- **맞는 전제도 "바로잡음"**: "영업이익이 왜 늘었어?"(실제로 늘었음)에 "질문의 전제와 달리 줄지 않고 크게 늘었습니다"라고 답함. 틀린 전제를 바로잡으라는 규칙만 있고 전제가 맞을 때의 지시가 없었음 → 전제가 맞으면 정정 표현 없이 확인만 하라고 명시 (네 방식 공통 규칙이라 비교 공정성 유지)

## 알려진 한계

- **지원 범위**: 미리 수집한 50개 종목 밖의 회사는 첫 질문 때 DART에서 받아오느라 느리고, 업종 비교는 이 50개 안에서만 합니다.
- **뉴스 검색의 남은 한계**: 페이지 넘김으로 몇 달 전 기사까지 닿게 됐지만, NAVER 검색은 최대 1,000건까지만 볼 수 있어 아주 오래된 기사나 검색량이 폭주한 종목은 여전히 못 닿을 수 있고, 검색어가 너무 구체적이면 결과 자체가 0건입니다. 처음 보는 기간 지정 검색은 여전히 한 번에 18~35초가 걸립니다(같은 검색을 다시 하면 캐시로 즉시).
- **심판과 답변 모델이 같음**: 둘 다 gpt-5.4-mini라 심판이 자기 문체를 후하게 볼 수 있습니다. 네 방식 모두 같은 답변 모델을 쓰므로 방식 간 비교는 공정하지만, 절대 점수는 다소 높게 나왔을 수 있습니다.
- **단위 환산 실수**: 조·억 환산을 LLM이 하다 보니 금액을 맞게 조회하고도 자릿수를 틀리는 경우가 있습니다(v3_2).
- **작은 골든셋, 1회 실행**: 29문항을 한 번씩만 돌렸고, h5 사례처럼 실행마다 결과가 달라져 통계적으로 약합니다.
- **held-out 독립성**: held-out도 프롬프트를 고친 쪽(개발자·AI 보조)이 작성해 완전히 독립적이지 않습니다. v1은 결과를 본 뒤 적용한 수정(재무 도구 강제, 증가율 채점, 뉴스 검색 개선)으로 오염되어 v2를 새로 만들었습니다. v2에서 발견한 도구 결함(연도 지정)도 고쳐서 v3를 새로 만들었고, v3에서도 도구 버그를 하나 고쳤으므로 다음 수정의 효과는 v4로 재야 합니다. 가장 좋은 것은 개발에 관여하지 않은 사람이 문항을 쓰는 것입니다.
- **LLM 심판의 불확실성**: 사람 라벨 7건으로만 검증했고, 입력이 같은 62건을 다시 채점했을 때 1건의 판정이 바뀌었습니다(이후 결과는 캐시로 고정). 쌍대 비교는 A/B 순서를 바꾸면 판정이 엇갈리는 경우가 있어(최종 실행에서 튜닝 셋 8/11, held-out 5/6만 일관) 엇갈린 건은 무승부로 처리합니다. 또 h5가 잘못 통과된 적이 있습니다(자기모순 답변).
- **재현성**: 뉴스는 실시간 검색이라 날짜에 따라 결과가 달라집니다. 생성된 답변은 `data/phase5_runs_export.jsonl`에 저장해 채점은 재현할 수 있게 했습니다.

```bash
# 지원 종목 50개 수집 (반도체 밸류체인 + 코스피 시총 상위, 로컬 SQLite: data/financials.db)
python -m src.data.build_universe --as-of 2026-09-23 --top 30

# 뉴스 배치 수집 (매일 돌리면 좋음, NAVER만 사용) + 최근 3일 기사 미리 임베딩
python -m src.data.collect_news --embed-days 3

# 평가
python -m src.eval.run_phase5               # 답변 생성(저장) + 채점
```
