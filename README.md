# stock-research-agent

**멀티홉 에이전틱 RAG 종목 리서치 어시스턴트.** "SK하이닉스 9월 주가 상승이 실적 때문이야?" 같은 복합 질문을 LLM 플래너가 쪼개고, DART 재무·뉴스·주가 세 가지 도구 중 필요한 것을 골라 여러 번 호출한 뒤, 근거를 인용해 답합니다.

이 프로젝트의 핵심 질문은 **"도구를 상황에 맞게 골라 쓰는 에이전트가 고정 파이프라인보다 실제로 나은가?"** 이고, 이를 자동 채점 파이프라인으로 측정합니다.

전체 설계/계획: [Notion 계획서](https://app.notion.com/p/3e43a009bcdf8178861eecf2eb6ad11e)

## 구조

```
질문 ─▶ 플래너 (src/agent/planner.py, ReAct 루프, gpt-5.4-nano, 최대 7스텝)
          │  질문의 전제("올랐다/줄었다")부터 데이터로 확인 → 필요한 도구 선택 → 결과 보고 재시도
          ├─▶ get_financial_data  DART 재무제표 (로컬 SQLite, 전년 동기·전기말 비교값 포함)
          ├─▶ search_news         NAVER 실시간 검색 + bge-m3 재정렬 (기간 필터, 페이지 넘김, 중복 기사 제거)
          └─▶ get_stock_price     KRX 주가·기간 수익률·PER/PBR/시가총액 (pykrx)
          ※ 재무 질문인데 재무 도구를 안 불렀으면 코드가 한 번 되돌려 조회하게 함
        ─▶ 초안 답변 ─▶ 검증 단계 (조회 자료와 대조: 틀린 수치 수정, 근거 없는 주장 삭제, 모순 정리)
        ─▶ 근거를 인용한 최종 답변
```

| 경로 | 내용 |
|---|---|
| `src/data/` | DART / NAVER / KRX 클라이언트, 재무 데이터·평가용 뉴스 코퍼스 수집 스크립트 |
| `src/agent/tools.py` | 도구 3개 (OpenAI function calling 스키마 + 실행 함수) |
| `src/agent/planner.py` | 플래너 에이전트 (Phase 4) |
| `src/agent/baseline.py` | 비교용 고정 파이프라인 3종 (Phase 3) |
| `src/agent/prompts.py` | 에이전트와 고정 파이프라인이 공유하는 프롬프트 규칙 (전제 검증, 답변 작성) |
| `src/eval/` | 골든셋, 채점기, LLM 심판, 도구 호출 경로 분석, 실험 러너 (Phase 5) |

## 평가 설계

### 비교군 (도구 구현은 모두 동일, 다른 건 "도구를 어떻게 조합하느냐"뿐)

| 방식 | 동작 |
|---|---|
| DART-only 고정 파이프라인 | 재무 도구만 1회 호출 후 답변 |
| News-only 고정 파이프라인 | 질문을 검색어로 1회 변환 → 뉴스 1회 검색 후 답변 |
| 3도구 항상 호출 고정 파이프라인 | 질문과 무관하게 세 도구를 전부 1회씩 호출 후 답변 ("그냥 다 부르면 되지 않나?"를 검증하는 가장 강한 비교군) |
| **플래너 에이전트** | 필요한 도구만 골라 여러 번 호출, 결과를 보고 재시도, 답변을 조회 자료로 한 번 더 검증 |

공정한 비교를 위해 세 가지를 맞췄습니다: 도구 함수 동일, 프롬프트 규칙(`prompts.py`) 공유, 출력 길이 제한 동일. 고정 파이프라인에는 질문 속 회사명을 미리 알려줘서 오히려 유리한 조건입니다. 반대로 "재무 도구 강제"와 "검증 단계"는 에이전트에만 있는 단계(LLM 호출 1회 추가)이므로, 결과 차이 중 일부는 이 단계 덕분입니다.

### 골든셋 (`src/eval/gold_set.py`)

- **튜닝 셋 11문항**: 재무 수치, 실적·주가 원인, 주가/PER, 재무 비율·기업 비교, 잘못된 전제. 개발 중 이 질문들을 보고 프롬프트·채점기를 고쳤기 때문에 **점수가 과대평가될 수 있습니다.**
- **held-out v1 6문항**: 결과를 보기 전에 확정한 질문 (부채비율, 매출 성장률, 다른 기간 수익률, PBR, 재무 데이터로 잘못된 전제 교정, 주가+재무+뉴스 멀티홉). 개발 중 h5를 보고 에이전트·채점을 고쳐 **일부 오염**됐습니다.
- **held-out v2 6문항 (주 지표)**: v1 오염 뒤 새로 만들어, 결과를 보기 전에 확정한 질문 (2025년 연간·3분기 보고서, 순이익률, "더 낮은 쪽" 기업 비교, 반대 방향 주가 전제, PER 밸류에이션 판단). 이 결과를 보고는 에이전트 프롬프트를 고치지 않습니다.
- 정답값은 하드코딩하지 않고 **채점 시점에 DART DB·KRX에서 직접 계산**합니다.

### 지표

| 지표 | 무엇을 재나 | 방법 |
|---|---|---|
| 수치 정확도 | 답변 속 숫자가 정답과 맞는지 | 규칙 기반. 조/억/만·%·배 표기를 파싱해 원본값과 대조 |
| 인용 P/R/F1 | 필요한 출처(도구)를 썼는지 | 질문별 정답 출처 라벨 vs 실제 호출한 도구 |
| LLM 심판 | 결론의 정확성·일관성, 원인 설명, 전제 교정, 근거 충실도(환각) | gpt-5.4-mini가 채점 기준 + 참고 정답 + **답변자가 조회한 자료**를 보고 pass/fail. 수치 일치는 코드 결과를 넘겨줌 |
| 쌍대 비교 | 에이전트 vs 3도구 항상 호출, 어느 답이 나은지 | A/B 순서를 바꿔 두 번 판정, 엇갈리면 무승부 (위치 편향 제거) |
| 도구 호출 경로 | 호출 수, 중복 호출, 결과가 빈 호출 | 저장된 실행 기록으로 계산 (API 호출 없음) |

**LLM 심판 자체도 검증했습니다.** 사람이 pass/fail을 매긴 7개 답변으로 심판과의 일치율을 쟀습니다:

| 심판 설정 | 사람 판단과 일치 |
|---|---|
| gpt-5.4-nano, 초기 | 4/7 |
| + 수치 확인은 코드에 맡기고 채점 기준 명확화 | 17/21 (7건 × 3회) |
| + 조회 자료 제공 (nano는 긴 입력에서 규칙을 어김) | 13/21 |
| **gpt-5.4-mini로 교체** | **21/21, 반복 판정 흔들림 없음** |

## 결과

23문항 × 4방식, 1회 실행 기준 (2026-09-24). 답변 모델은 모두 gpt-5.4-nano, 심판은 gpt-5.4-mini입니다.

### held-out v2 6문항 — 주 지표

v1 held-out이 개발 중 일부 오염되어(아래 참고) 새로 만든 셋입니다. 결과를 보기 전에 확정했고, 튜닝 셋·v1과 겹치지 않는 유형(2025년 연간/3분기 보고서, 순이익률, "더 낮은 쪽" 비교, 반대 방향 주가 전제, PER 밸류에이션 판단)으로 구성했습니다.

|---|---|---|---|
| DART-only 고정 파이프라인 | 0.77 | 2/6 | 1/6 |
| News-only 고정 파이프라인 | - | 1/6 | 0/6 |
| 3도구 항상 호출 고정 파이프라인 | 0.56 | 3/6 | 2/6 |
| **플래너 에이전트** | **0.88** | **5/6** | **5/6** |

쌍대 비교 (에이전트 vs 3도구 항상 호출): **4승 0패 2무**.

### 해석

- **에이전트의 우위는 "도구 선택과 파라미터"에서 나옵니다.** v2에서 에이전트만 통과한 문항은 2025년 연간 매출(연간 보고서를 골라 조회), 부채비율이 더 낮은 쪽 비교(두 회사를 각각 조회해 31.1% 대 32.8% 비교), 반대 방향 주가 전제("왜 떨어졌어?"에 실제 +6.83%로 교정)였습니다. 고정 파이프라인은 최신 보고서·회사 하나·최근 30일로 고정돼 있어 구조적으로 못 푸는 문제들입니다.
- **단순 조회와 계산은 차이가 없습니다.** 순이익률(v2_3), PBR·부채비율(v1)처럼 최신 데이터 하나로 풀리는 질문은 "3도구 항상 호출"도 맞힙니다.
- **에이전트가 v2에서 틀린 1건은 도구 설계 결함이었습니다.** "2025년 1~9월 누적 영업이익"에서 재무 도구에 연도를 지정할 방법이 없고 조회 가능한 보고서 목록도 보이지 않아, 에이전트가 최신(2026 반기)만 보고 "자료 없음"으로 포기했습니다. 도구에 `year` 파라미터와 보고서 목록을 추가해 고쳤지만, v2 점수는 수정 전 결과 그대로 둡니다.
- **실적 원인 설명(q5·q6)은 여전히 약합니다.** 근거 기사는 찾게 됐지만 nano가 "추정"을 사실처럼 섞어 씁니다.
- **1회 실행이라는 한계는 그대로입니다.** 같은 질문에서도 실행마다 에이전트 행동이 달라지는 것을 확인했으므로(h5), 반복 실행 평균이 있어야 더 확실히 말할 수 있습니다.

## 개발 중 발견한 문제와 해결

평가를 만들면서 발견한 문제들입니다. 대부분 "비교가 공정하지 않았다" 또는 "채점이 틀렸다" 유형이었습니다.

- **API 키 로드 누락**: 클라이언트 코드 어디에도 `load_dotenv()`가 없어, 셸에 키를 export하지 않으면 DART가 HTML 에러 페이지를 반환 → 추가
- **News-only 비교군이 질문 문장을 그대로 검색어로 사용**: 에이전트만 검색어를 만들고 있어 불공정 → 비교군에도 검색어 생성 단계 1회 추가
- **골든셋 문구의 모호함**: "반기 매출액"이 분기 단독(171조)과 상반기 누적(305조) 둘 다로 읽혀 채점이 운에 좌우됨 → "1~6월 누적"으로 명시
- **비교군만 답변을 300토큰으로 자름**: 수치를 말하기 전에 답변이 잘려 불공정 → 제한 제거
- **심판이 "305조 3,729억"을 원 단위와 대조하지 못함**: 친절한 한국어 단위를 쓰는 답변만 불리 → 수치 확인은 코드가, 심판은 논리만
- **검색 기간 규칙 결함**: "보고서 기간 안에서만 검색"하게 했는데, 실적 원인 기사는 대부분 기간이 끝난 뒤 실적 발표 때 나옴 → 기간 종료 후 2개월까지 검색
- **에이전트 자기모순**: 계산 전에 결론부터 써서 "삼성전자가 더 높다… 따라서 SK하이닉스가 더 높다"가 두 번 재현 → "계산 먼저, 결론은 마지막에 한 번" 규칙
- **재무 도구 없이 수치를 지어냄**: "영업이익이 왜 줄었어?"(실제로는 증가)에 대해 재무 도구를 부르지 않고 전년 수치를 115.8조로 지어내(실제 16.7조) 틀린 전제를 받아들인 실행이 있었음 → 재무 용어가 있는 질문에서 재무 도구를 안 불렀으면 코드가 한 번 되돌림. **held-out(h5)에서 발견한 문제라, 이 수정 이후 h5는 깨끗한 held-out이 아닙니다.**
- **근거 없는 원인 끼워 넣기, 결론 모순**: 기사를 찾아와도 자료에 없는 원인("성과급")을 넣거나 "전제가 맞습니다… 증가했습니다"처럼 앞뒤가 다른 답이 나옴 → 초안을 조회 자료와 대조하는 검증 단계 추가
- **채점 기준이 환각을 부추김**: "원인을 최소 2가지 제시", "세 카테고리 모두 근거 있는 원인" 같은 기준은, 근거가 원인 하나만 뒷받침할 때 나머지를 지어내야 통과하는 구조였음 → 개수 대신 "근거 있는 원인 제시, 못 찾은 부분은 솔직히 밝히면 통과, 지어내면 fail"로 수정 (튜닝 셋 q5·q6만. held-out은 그대로)
- **증가율 문항의 수치 채점 설계 오류**: 증가율(%)만 정답으로 봐서, 금액 두 개("전년 16.7조 → 당기 98.2조")로 답하면 틀린 것으로 처리됨 → 금액 두 개를 정확히 제시해도 정답으로 인정. held-out(h5) 채점 방식을 결과를 본 뒤 고친 것이라 명시해 둡니다 (모든 방식에 똑같이 적용).
- **재무 도구에 연도 지정이 없음**: "2025년 1~9월 누적 영업이익"에서 에이전트가 최신 보고서만 보고 포기함. 도구가 연도를 받지 않고 조회 가능한 보고서 목록도 주지 않아 재시도할 단서가 없었음 → `year` 파라미터와 보고서 목록 추가. held-out v2에서 발견했으므로 v2 점수는 수정 전 결과로 둠
- **채점기 정규식 버그**: 조/억/만 금액 패턴이 숫자 없이 쉼표만 있어도 매칭돼, 답변에 "비용, 억제" 같은 표현이 나오자 `", 억"`을 금액으로 읽으려다 채점이 멈춤 → 숫자로 시작해야 매칭되게 고치고 단위 테스트 추가
- **뉴스 검색이 첫 페이지만 봄**: 첫 100건은 인기 종목이면 최근 두 달치뿐이라 몇 달 전 기사가 "존재하는데도" 못 가져옴 → 기간 지정 시 최대 10페이지(1,000건)까지 넘겨 수집하고, 임베딩 전에 키워드 사전 필터로 80건으로 줄임 (CPU에서 500건 임베딩이 66초라서). 튜닝 셋에서 0건이던 검색어가 기간 내 기사 184~514건으로 늘었습니다. 대가로 기간 지정 검색 한 번에 18~35초가 걸립니다.

## 알려진 한계

- **지원 범위가 좁음**: 재무 데이터는 삼성전자·SK하이닉스의 최근 보고서 4개만 로컬 DB에 있습니다.
- **뉴스 검색의 남은 한계**: 페이지 넘김으로 몇 달 전 기사까지 닿게 됐지만, NAVER 검색은 최대 1,000건까지만 볼 수 있어 아주 오래된 기사나 검색량이 폭주한 종목은 여전히 못 닿을 수 있고, 검색어가 너무 구체적이면 결과 자체가 0건입니다. 기간 지정 검색은 한 번에 18~35초가 걸립니다.
- **답변 모델의 근거 활용**: 근거 기사를 찾아와도 nano가 "추정"을 사실처럼 섞어 써서 실적 원인 설명 문항(q5·q6)이 계속 떨어집니다. 답변 모델을 키우면 나아질 수 있지만 비용이 늘고, 비교군도 같이 바꿔야 공정합니다.
- **작은 골든셋, 1회 실행**: 17문항을 한 번씩만 돌렸고, h5 사례처럼 실행마다 결과가 달라져 통계적으로 약합니다.
- **held-out 독립성**: held-out도 프롬프트를 고친 쪽(개발자·AI 보조)이 작성해 완전히 독립적이지 않습니다. v1은 결과를 본 뒤 적용한 수정(재무 도구 강제, 증가율 채점, 뉴스 검색 개선)으로 오염되어 v2를 새로 만들었습니다. v2에서 발견한 도구 결함(연도 지정)도 고쳤으므로, 그 수정의 효과를 재려면 다음 held-out(v3)이 필요합니다. 가장 좋은 것은 개발에 관여하지 않은 사람이 문항을 쓰는 것입니다.
- **LLM 심판의 불확실성**: 사람 라벨 7건으로만 검증했고, 입력이 같은 62건을 다시 채점했을 때 1건의 판정이 바뀌었습니다(이후 결과는 캐시로 고정). 쌍대 비교는 A/B 순서를 바꾸면 판정이 엇갈리는 경우가 있어(최종 실행에서 튜닝 셋 8/11, held-out 5/6만 일관) 엇갈린 건은 무승부로 처리합니다. 또 h5가 잘못 통과된 적이 있습니다(자기모순 답변).
- **재현성**: 뉴스는 실시간 검색이라 날짜에 따라 결과가 달라집니다. 생성된 답변은 `data/phase5_runs_export.jsonl`에 저장해 채점은 재현할 수 있게 했습니다.

## 실행 방법

```bash
pip install -r requirements.txt
cp .env.example .env   # DART / NAVER / OpenAI 키, KRX 로그인 정보 입력
```

| 키 | 용도 | 비고 |
|---|---|---|
| `DART_API_KEY` | 재무 데이터 | opendart.fss.or.kr, 무료 |
| `NAVER_CLIENT_ID` / `NAVER_CLIENT_SECRET` | 뉴스 검색 | NAVER API HUB, 무료 (일 25,000건) |
| `OPENAI_API_KEY` | 에이전트·심판 LLM | 유료 |
| `KRX_ID` / `KRX_PW` | PER/PBR/시가총액 | data.krx.co.kr 회원 아이디/비밀번호. 일별 주가는 로그인 없이도 조회됨 |

```bash
# 재무 데이터 수집 (로컬 SQLite: data/financials.db)
python -m src.data.collect_financials

# 에이전트에 직접 질문
python -c "from src.agent.planner import run_agent; print(run_agent('SK하이닉스 상반기 영업이익률은?')['answer'])"

# 평가
python -m src.eval.run_phase5               # 답변 생성(저장) + 채점
python -m src.eval.run_phase5 --regrade     # 생성 없이 저장된 답변으로 채점만 (채점기를 고쳤을 때 API 절약)
python -m src.eval.run_phase5 --resume      # 끊긴 생성 이어서
python -m src.eval.run_phase5 --skip-judge  # LLM 심판 없이 (OpenAI 호출 없이 흐름 점검)
python -m src.eval.run_phase5 --questions h1_debt_ratio --approaches agent   # 일부만
```

실행 결과는 `logs/phase5_eval.md`(질문·조회 자료·답변·채점 근거 전체)와 `data/phase5_summary_export.md`(요약 표)에 남습니다. 둘 다 로컬 파일이며 git에는 올리지 않습니다. LLM 심판 응답은 `data/judge_cache_export.json`에 캐시되어, 다시 채점할 때 입력이 바뀐 답변만 심판을 호출합니다.

```bash
python -m unittest discover tests   # 채점기 단위 테스트 (API 호출 없음)
```
